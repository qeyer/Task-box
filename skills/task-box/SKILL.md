# 任务收纳

## 核心原则

先建立任务边界，再开始产生文件。目录结构必须由实际工作流程决定，不套固定模板，也不预建没有用途的空目录。

## 第一步：确定项目根目录

按以下优先级选择：

1. 用户明确给出的项目路径。
2. 当前工作区根目录。
3. 当前目录中明显的项目根。

存在多个可能根目录且选择会改变文件归属时，只问一次用户。不得把任务建到下载目录、桌面或项目根之外，除非用户明确指定。

## 第二步：判断是否新任务

- 用户说“新任务”“新支线”“单独建文件夹”：创建新的任务目录。
- 用户说“继续之前的任务”：先查找同名目录和 `任务说明.md`，确认后复用。
- 同名目录已经存在但用户没有说继续：不要覆盖或自动合并；建议新名称或日期后缀。

## 第三步：根据任务设计最小目录

先识别：

- 输入文件是什么。
- 中间过程会产生什么文件。
- 是否需要审核预览。
- 最终交付是什么。
- 是否需要保留旧版本或归档。

只为确定会出现的文件创建目录。读取 [references/directory-decision-guide.md](references/directory-decision-guide.md) 选择结构，但不要机械复制示例。

通用规则：

- 只有一个输入文件时，可以直接放在任务根目录，不必创建“输入”文件夹。
- 没有审核环节时，不创建“预览”。
- 没有多个版本时，不创建“归档”。
- 脚本很少时，可直接放“工作文件”，不另建“脚本”。
- 最终交付始终与过程文件分开。

## 已有代码仓库的例外

不要为了整理任务而搬动或复制仓库源代码。代码继续遵循原项目结构。

若用户仍需要独立任务边界，只在仓库约定的位置创建任务资料目录，例如：

- `tasks/<任务名>/`
- `docs/tasks/<任务名>/`
- 项目已有的工作记录目录

其中只放需求、计划、测试证据、截图和导出物。修改后的源代码仍留在原有 `src/`、`tests/` 等位置。

## 第四步：生成计划 JSON

在临时位置写入 UTF-8 JSON，结构参考 [references/example-plan.json](references/example-plan.json)：

```json
{
  "project_root": "项目根目录绝对路径",
  "task_name": "用户可读的任务名称",
  "task_folder": "任务文件夹名称",
  "goal": "一句话目标",
  "folders": [
    {"path": "实际需要的目录", "purpose": "这里放什么"}
  ],
  "deliverables": ["最终交付物"]
}
```

`task_folder` 必须是项目根目录下的单层目录名。子目录可使用 `工作文件/脚本` 这样的相对路径，但不能包含 `..` 或绝对路径。

## 第五步：创建工作区

从 Skill 根目录执行：

Windows：

```powershell
python scripts/create_workspace.py "<计划 JSON 绝对路径>"
```

macOS / Linux：

```bash
python3 scripts/create_workspace.py "<计划 JSON 绝对路径>"
```

创建器会：

- 验证任务路径位于项目根目录内。
- 拒绝覆盖现有同名目录。
- 只创建 JSON 中列出的子目录。
- 生成 `任务说明.md`，记录目标、目录用途和计划交付。

## 第六步：执行任务

创建完成后，后续新增内容默认只能写入任务目录：

- 用户素材原地保留；需要副本时复制到任务目录，不擅自移动。
- 脚本、清单、截图、预览和成品分别放入其对应目录。
- 临时文件放在任务目录内的临时位置，任务完成后清理。
- 不把中间文件散落在项目根目录。

每次创建新类型文件前，先判断现有目录能否容纳；只有确实出现新的文件类别时才新增目录，并同步更新 `任务说明.md`。

## 安全边界

- 不删除、覆盖或批量移动用户现有文件，除非用户明确授权。
- 递归移动或删除前必须验证绝对路径仍在目标项目或任务目录内。
- 不因为整理而重命名用户提供的原始素材。
- 不静默合并同名任务。
- 不修改其他支线任务目录。

## 完成反馈

创建后简洁报告：

1. 任务目录的绝对路径。
2. 实际创建的目录树。
3. 为什么选择这些目录。
4. 下一步准备把哪些文件放到哪里。

不要展示没有创建的“标准模板目录”。
